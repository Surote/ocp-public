01 — The Big Picture

Request Flow

Every inference request passes the same Envoy filter chain. On RHOAI 3.5 two external processors bracket the Kuadrant policy shim: ipp-pre reads the model name out of the body before auth, so OpenAI-standard POST /v1/chat/completions works with no path prefix; ipp runs after policy and rewrites the request for the backend. Traffic never leaves Envoy for a detour — Authorino and Limitador are gRPC callouts.

02 — On the Wire

Step-by-Step Request Journey

What happens, hop by hop, when a client sends POST /v1/chat/completions with {"model":"gpt-5.6-luna"} — the body-based form that any OpenAI SDK produces unmodified. The legacy path form POST /swongpai-vllm/gpt-5.6-luna/v1/chat/completions takes the same route; only the identity lookup in step 4 differs. Filter order below was read from the gateway's Envoy config_dump, not from CRs.

1
Client → AWS Classic ELB
HTTPS 443
Client resolves maas.apps.<cluster-domain> (Route53 → ELB <elb>.…elb.amazonaws.com) and sends the request with Authorization: Bearer sk-oai-…. The ELB forwards raw TCP — no TLS termination here.
2
ELB → Envoy Gateway
TLS terminate
Pod maas-default-gateway-openshift-default (an istio-proxy Envoy programmed by istiod-openshift-gateway — OpenShift 4.20's built-in Gateway API, no Service Mesh operator) terminates TLS with maas-gateway-tls, a copy of the ROSA wildcard cert (expires 2026-11-09, rotated by CronJob). The HTTP filter chain that follows is: ext_proc.ipp-pre → wasm (Kuadrant) → ext_proc.ipp → router.
3
Envoy → payload-pre-processing
gRPC ext_proc :9004
ipp-pre streams the request body (FULL_DUPLEX_STREAMED), reads .model and promotes it to a header: X-Gateway-Model-Name: gpt-5.6-luna, plus x-ipp-selected-provider: openai-prod for external models. It then clears Envoy's route cache so routing re-evaluates with the new headers. Configured failure_mode_allow: true — if it dies, body-based routing breaks but path-based requests keep flowing. This is the piece that makes step 4 possible before policy, closing RHAISTRAT-1540.
4
Envoy wasm → Authorino
gRPC ext_authz :50051
The Kuadrant shim sends a CheckRequest. On 3.5 there is one gateway-scoped AuthPolicy, maas-gateway-auth, not one per model. Authentication is three rules: keys matching ^Bearer sk-oai-.* (priority 0), the same key in an x-api-key header (priority 1, for clients that cannot set Authorization), and Kubernetes TokenReview (priority 2, only when neither key form is present) — so oc whoami -t works on every path, not just /v1/models. A key form triggers a metadata call to maas-api:8443/internal/v1/api-keys/validate, cached 60s per key. Authorization is five rules: auth-valid, require-group-membership (derives a model identity — ns/name from the path if it has two segments, else the X-Gateway-Model-Name header — and looks it up in a generated allow-map; here gpt-5.6-luna → cluster-admins), deny-client-identity-headers (rejects client-supplied x-maas-username / x-maas-group), subscription-valid (a second maas-api lookup, /internal/v1/subscriptions/select, also cached 60s) and tenant-gateway-isolation, which is a stub today. Verdicts cached 60s. Full ruleset in section 09. Failure → 401 / 403. A bare Access denied almost always means the identity string is not an allow-map key — a naming mismatch.
5
Authorino → Envoy
identity metadata
On success Authorino returns OK plus identity metadata: userid, groups, and selected_subscription_key — e.g. models-as-a-service/gpt-5-6-luna-subscription@swongpai-vllm/gpt-5.6-luna. The key was minted against one subscription; that string is what the rate limiter matches on in the next step.
6
Envoy wasm → Limitador
gRPC ratelimit :8081
Does auth.identity.userid still have budget? The route's TokenRateLimitPolicy maas-trlp-gpt-5.6-luna carries one limit per subscription that includes the model: 100 000 tokens / 1h for gpt-5-6-luna-subscription, 90 000 / 1s for sa-premium (/v1/models exempt). A gateway-wide gateway-default-deny (limit 0) covers any path that is not a model route or /maas-api, /v1/models, /v1/subscriptions, /v1/api-keys. Over budget → 429.
7
Envoy → payload-processing
gRPC ext_proc :9004
ipp runs after policy and is failure_mode_allow: false — if this pod is down, every inference request fails. Not quite every request: the four maas-api routes set disabled: true for this filter, so key minting and /v1/models keep answering. Its stages: maas-headers-guard (strip MaaS identity headers), stream-usage-enforcer (force stream_options.include_usage on streamed responses), model-provider-resolver, api-translation (rewrite :path to /v1/chat/completions; for Anthropic providers also the body), and apikey-injection (replace the client's Authorization with the provider key from Secret openai-api-key, label inference.llm-d.ai/ipp-managed). For an internal vLLM model these stages are no-ops except the header guard.
8
Envoy: HTTPRoute match
router
External: HTTPRoute/gpt-5.6-luna (owned by the ExternalModel) matches X-Gateway-Model-Name: gpt-5.6-luna + x-ipp-selected-provider: openai-prod on PathPrefix /, sets Host: api.openai.com, and forwards to Service/openai-prod — an ExternalName with a ServiceEntry (MESH_EXTERNAL) and a DestinationRule (TLS SIMPLE) named after the provider, shared by every model on it. Timeout 300s.
Internal: …-kserve-route (owned by the LLMInferenceService) matches /swongpai-vllm/<model>/v1/{completions,chat/completions,responses,messages} and the newer /publishers/swongpai-vllm/models/<model>/… form, URL-rewrites the prefix away, and sends to InferencePool/muse-glimmer-llmd-inference-pool:8000 — on the one model that sets router.scheduler, so a per-route ext_proc override asks the EPP which pod to use before the router picks an endpoint. A body-based call to the same model matches the exact-path-plus-header rule, which also backs onto the InferencePool — the per-endpoint counters show it, and the …-kserve-workload-svc cluster has never served a request. What it misses is the scheduling decision: the EPP is consulted at filter 3, before ipp-pre has set the header the pool rule matches on. Only the bare / catch-all names the workload Service at all. Full route table in section 05.
9
Response → payload-processing
ext_proc response path
ipp also processes the response (response_body_mode: FULL_DUPLEX_STREAMED) — translation for non-OpenAI providers, and stream-usage-enforcer to make sure a streamed reply carries a usage block at all. The token debit itself is not ipp's. Corrected 2026-09-19 against the loaded wasm configuration: the Kuadrant shim runs a second action per request against ratelimit-report-service, whose ratelimit.hits_addend is the CEL expression responseBodyJSON("/usage/total_tokens"). So Envoy reads the count out of the response body and reports it to Limitador directly; ipp only has to make sure the field is there to read. This is how the limit is tokens, not requests. The body reaching the client is unchanged.
10
Envoy → Client
HTTPS 200
The response returns to the client. In parallel the TelemetryPolicy/maas-telemetry supplies the label set — model (from the response body), user, subscription, organization_id and cost_center — and those labels land on Limitador's counters, not on Envoy's own metrics: authorized_hits_total carries model, user and subscription, while istio_requests_total carries none of them. The two empty-by-default labels are dropped rather than stored, so grouping by cost centre works only once a subscription sets tokenMetadata. Since tenant telemetry was enabled on MaasTenantConfig (2026-09-11) the policy is written by maas-controller with has(...) ? ... : "" guards, so the old CelError::Resolve flood on RHCL 1.4.x is gone. Trace sampling is configured — DSCI spec.monitoring.traces.sampleRatio: "0.1" and an Instrumentation/data-science-instrumentation with traceidratio 0.1 — but nothing on this path is instrumented, so the sampler never has a span to sample: Tempo holds zero traces and the collector has never exported one. 03 — Before the First Request

Where API Keys Come From

Inference needs a key. Keys are minted by maas-api — which on 3.5 lives in its own namespace, redhat-ai-gateway-infra — scoped to a subscription, and stored in PostgreSQL. The subscription, not the key, decides which models you reach and how many tokens you get. Three subscriptions exist today — sa-premium (5 modelRefs), gpt-5-6-luna-subscription, claude-sub — all at priority: 0, which the controller flags as SharedPriority. Max lifetime 90 days; expired keys are swept every 15 minutes.

The Same Gateway as Running Pods — Where the Bytes Actually Go

The graph above is objects and references. This one is one request, drawn as a line that physically runs through every block it passes: client, load balancer, into the Envoy pod, through the filters in the order Envoy executes them, out to exactly one backend. The blue line is the request. Where a filter has to ask another pod something, the line does not divert — a double-headed orange arrow drops to that pod and comes back, because the request waits in Envoy while a separate gRPC connection carries what the processor needs. That distinction is the point of the drawing: ipp-pre, ipp and the EPP genuinely receive the payload over those calls (FULL_DUPLEX_STREAMED, over TLS), but none of them ever forwards the request onward — only Envoy does. Pods, ports, TLS and filter order read live on 2026-09-19 from config_dump and the loaded wasm configuration.

The ordering above is not cosmetic, and it is the one thing this diagram corrects. The endpoint picker is filter 3 of 14 — ahead of ipp-pre (9) and the Kuadrant shim (10) — so on a route that carries the per-route override, Envoy asks the scheduler which pod should serve before it has established that the caller may call anything at all. Measured on 2026-09-19: two curls to the path-based URL with no Authorization header both returned 401, and inference_extension_scheduler_attempts_total went from 11 to 13 anyway. Two consequences worth holding on to: the scheduler's request count is attempts, not served requests, so it will drift above the number of successful inferences on a gateway that sees bad keys; and an unauthenticated caller can make the EPP do work, which is cheap at 51 µs but is not nothing. It also gives the body-based bypass a second, sturdier explanation — at filter 3 the model header does not exist yet, so the route in hand cannot be an InferencePool rule, and by the time filter 9 has set the header and the route has been re-matched, filter 3 is behind us.

Three things about this triple that are not obvious:

1. They are joined by a hostname string, not by references. Service.spec.externalName, ServiceEntry.spec.hosts[0] and DestinationRule.spec.host all just say api.openai.com. Nothing validates that they agree. Change one and the others keep reporting healthy while TLS origination quietly stops applying.

2. SNI comes from the HTTPRoute, not from the DestinationRule. The cluster sets auto_sni: true and auto_san_validation: true with no explicit sni field, so Envoy takes both the SNI it sends and the name it validates the certificate against from the Host header — which is set by the route's RequestHeaderModifier. Drop that filter and the handshake fails on a name mismatch, not on anything visible in the Istio config.

3. Validation uses the system root store. SIMPLE with no caCertificates resolves to the SDS secret file-root:system. Fine for public providers; a provider behind a corporate TLS-inspecting proxy or a private CA would need caCertificates added to the DestinationRule — and that object is owned by the ExternalProvider, so the edit has to go in the CR, not the rule.

Why Classic Load Balancing Fails for LLMs

Round-robin and least-connections assume all requests cost roughly the same and any backend can serve them equally well. Both assumptions break for LLMs:

  1. Requests are wildly unequal. A 10-token prompt and a 10,000-token prompt differ by ~1000× in prefill compute. "Number of connections" tells you nothing about actual GPU load — one pod may hold 3 trivial requests, another 1 giant one.
  2. Backends are not interchangeable — KV cache makes them stateful. When a vLLM pod processes a prompt, it stores the computed attention keys/values (KV cache) in GPU memory. A follow-up request sharing that prefix (same system prompt, same chat history) can skip recomputation only if it lands on the same pod. Blind balancing throws that away and repays full prefill cost on every hop.
  3. Generation length is unknown at admission. A request that generates 4,000 tokens occupies KV memory for its whole lifetime. Queue depth right now is a weak signal for load 30 seconds from now — you want scheduling that reads engine-level signals, not TCP-level ones.

llm-d's answer: pull the routing decision out of the proxy and give it to a model-aware sidecar service — the Endpoint Picker (EPP). Envoy still moves the bytes; the EPP decides where.

Full request lifecycle through the EPP:

  1. Envoy matches the HTTPRoute to the InferencePool and opens an ext_proc conversation with the EPP, streaming request headers + body.
  2. The tokenizer sidecar converts the prompt to token IDs — the same tokenization the model itself will use (its modelcar container symlinks the model files at /mnt/models).
  3. The prefix-cache index is consulted: longest-prefix match of those token IDs against each pod's known KV blocks (index kept current by ZMQ KV events, not polling).
  4. queue-scorer reads current queue depth per pod; both scorers emit 0–1 scores.
  5. max-score-picker computes Σ(score × weight) and picks the winner.
  6. EPP returns the chosen pod's address in a routing header; Envoy forwards the request to that exact pod — not the Service VIP.
  7. The pod runs inference; new KV blocks it creates are announced over ZMQ, updating the index — so the next turn of this conversation scores a hit and sticks to the same pod.

If the EPP itself dies: the InferencePool is configured failureMode: FailOpen — Envoy falls back to cache-blind balancing across the pool. Latency degrades; traffic survives.

Beyond This Cluster — the llm-d Ladder

llm-d defines three "well-lit paths" — proven deployment profiles in increasing order of scale. This cluster runs the first. Evidence the higher rungs are already wired in: the LLMInferenceService status carries preset annotations for config-llm-prefill-template and config-llm-decode-worker-data-parallel — unused at replicas: 1 on a single GPU, but one spec change and one more GPU away.

this cluster

1 · Intelligent Inference Scheduling

Identical replicas + EPP with queue & prefix-cache scorers. Lower TTFT and higher goodput than any cache-blind balancer, with no change to the model pods themselves. Fits single-node and modest multi-GPU setups.

next rung

2 · Prefill / Decode Disaggregation

Split the two phases onto different pods: prefill is compute-bound (long prompts), decode is memory-bandwidth-bound (token streaming). large scale

For giant Mixture-of-Experts models (DeepSeek-R1 class): experts sharded across many GPUs/nodes with data-parallel attention, deployed as multi-node leader/worker groups. The EPP's role grows to routing across heterogeneous multi-node serving groups.

Can You Mix Modes?

Mixed-Mode Deployments

Yes — across models. No — within one model.

Each LLMInferenceService is an independent deployment with its own mode. On the same cluster you can run:

  • Llama 8B in unified mode (2 replicas, simple, fast cold-start) — for lightweight tasks
  • Llama 70B in disaggregated mode (prefill pool + decode pool) — for long-context, latency-sensitive workloads
  • DeepSeek-R1 in multi-node expert mode — for research/batch workloads needing the largest models

Each gets its own HTTPRoute and MaaS policies. Models with router.scheduler also get their own InferencePool and EPP; models without it use plain Service routing. They share the Gateway and MaaS control plane (maas-api, Authorino, Limitador). Subscriptions and rate limits are per-model — fully independent quota management.

What you cannot do: hybrid replica roles within a single model — e.g., "some replicas do both prefill+decode, some specialize." The CRD is binary at the pod level: spec.prefill present → separate prefill and decode pools. Absent → all unified.

But per-request hybrid exists: in a disaggregated deployment, the scheduler's threshold parameter routes only long prompts (estimated tokens > N) through the prefill pool — short prompts are handled entirely by the decode pod, skipping the KV-transfer round trip. So a P/D deployment with threshold > 0 behaves like unified mode for small requests and disaggregated mode for large ones — the closest thing to "mixed" within one model.

How It Works

The mechanics behind the diagrams — with the actual 3.5 configuration from the live cluster, collapsible below each explanation.

Three Chains of Command

The platform chain (operator → infra): Setting aigateway.modelsAsAService.managementState: Managed in the DSC makes maas-controller bootstrap a Config/default, which owns an AITenant (tenant namespace ↔ Gateway), a MaasTenantConfig, the maas-api Deployment in redhat-ai-gateway-infra, its HTTPRoute, the payload-processing EnvoyFilter and a Limitador ServiceMonitor. The 3.4 Tenant is still there, annotated deprecated, and ignored.

The activation field moved, and the old one is now explicitly off. Read live on 2026-09-19: spec.components.aigateway is {managementState: Managed, modelsAsAService: {managementState: Managed}} while spec.components.kserve.modelsAsService is {managementState: Removed}. Anything — including earlier passes of this page and the repo's own notes — that tells you to flip the field under kserve is describing a path this cluster has abandoned. Patching it would be a no-op at best.

The intent chain (humans → policy): Admins write MaaSAuthPolicy (who may reach which models), MaaSSubscription (how many tokens), MaaSModelRef (which model). maas-controller compiles all auth policies into one gateway-scoped Kuadrant AuthPolicy with an OPA allow-map, and each subscription into a TokenRateLimitPolicy on the model's HTTPRoute.

The serving chain (model → backend): Internal — an LLMInferenceService is expanded by llmisvc-controller into vLLM Deployment, Services and HTTPRoute. External — an ExternalProvider + ExternalModel pair yields an ExternalName Service, ServiceEntry, DestinationRule and HTTPRoute. Either way the chains meet only at the HTTPRoute.

Deny by Default

Three gateway-wide policies enforce a zero-trust posture; on 3.5 only the first is what actually decides:

  1. maas-gateway-auth — Enforced. Authenticates API keys or Kubernetes tokens, then authorizes by looking the request's model identity up in the allow-map. A model with no MaaSAuthPolicy has no key in the map → Access denied.
  2. gateway-default-deny — a TokenRateLimitPolicy with limit: 0 for any path that isn't a maas-api path. Reports Enforced=False (overridden): every model route carries its own TRLP that takes precedence. It only bites on routes with no subscription.
  3. maas-default-gateway-authn — the 3.4-era k8s TokenReview + SubjectAccessReview policy. Also Enforced=False; its job moved into maas-gateway-auth's openshift-identities rule.

Adding a model therefore adds exactly two keys to one allow-map (<name> and <ns>/<name>) and one TRLP — everything else stays shut. Deleting a model does not prune its allow-map key.

An external model's route matches on headers that ipp-pre injected, so the client never needs a path prefix. An internal model's route is the classic prefix-and-rewrite. Both attach to the same Gateway and both are policy targets.

Authentication & Authorization — the Full Ruleset

Two AuthPolicy objects target this Gateway: maas-default-gateway-authn, hand-written, and maas-gateway-auth, compiled by maas-controller — the second is the one that carries the identity and allow-map rules. Re-read live on 2026-09-19, and it has grown since this section was first written: three authentication rules — api-keys (^Bearer sk-oai-.*, priority 0), api-keys-x-api-key (the same key in an x-api-key header, priority 1, for clients that cannot set Authorization — Anthropic SDKs among them) and openshift-identities (Kubernetes TokenReview, priority 2, only when neither key form is present) — and five authorization rules: auth-valid, deny-client-identity-headers, require-group-membership, subscription-valid and tenant-gateway-isolation. Cache keys include the model identity, so a verdict is per user × model for 60s.

RuleWhat it actually enforces, from the live policy
deny-client-identity-headers Rejects any request that already carries x-maas-username or x-maas-group. Those headers are written by this policy's success response and then read downstream by the access log, so a client that could set them would be forging its own identity in the usage record. Cheap rule, load-bearing.
auth-valid · require-group-membership The allow-map pair: is this key valid, and is the caller in a group the model's MaaSAuthPolicy admits.
subscription-valid Depends on the subscription-info metadata call below — a subscription must be selectable for this caller and model.
tenant-gateway-isolation A stub, and it says so in its own rego: "Replace with a real maas-api call to validate that the API key's tenant matches the gateway hostname". Today it does not stop a key issued for one tenant being used against another tenant's hostname. Worth knowing before treating hostname as a security boundary.

Two of the rules reach into maas-api. The policy's metadata stage has apiKeyValidation → POST /internal/v1/api-keys/validate, which runs only when an sk-oai key is present, and subscription-info → POST /internal/v1/subscriptions/select, gated on the path looking like a model path or x-gateway-model-name being set — which is every inference call, whatever credential it used. Both are cached with ttl: 60, keyed on the API key and on caller × model respectively, so the backend sees roughly one call per key and per caller-model each minute rather than one per request. The consequence for the failure table below is unchanged in kind and delayed in time: with maas-api down, inference keeps working off warm cache entries and then fails as they expire, for Kubernetes-token callers too — subscription-valid depends on that lookup regardless of how the caller authenticated.

How it was tested

  1. Path. Python threads on a laptop, one per simulated user, POST to /v1/chat/completions on the MaaS hostname with model publishers/swongpai-vllm/models/muse-glimmer-llmd and an sk-oai key on sa-premium (minted for the test, revoked after). Nothing bypasses the ELB, AuthPolicy, token limits, payload-processing or the EPP. vLLM's /metrics is only read (oc exec) to see inside the engine.
  2. Coding-agent session. Shared ~8k-token system prompt (identical across sessions, like an agent's tool definitions) + ~12k-token task context; each turn appends the model's reply plus ~3k tokens of "tool output"; 6 turns, 300 output tokens, 5s think time. Context grows to ~34k — the range real opencode calls hit in this cluster's usage logs (16k–38k).
  3. Arrival. Up to 32: all sessions start together (worst case). 32–100: starts spread uniformly over 60s, like people beginning work — this also keeps the auth burst problem below out of the result.
  4. Prompts. Random words with a unique tag per session (2.6 tokens/word, measured), so the prefix cache only hits where a real agent would hit it. ignore_eos pins output length.
  5. Safety rails. CPU, memory and restarts of the gateway pod, payload-processing, maas-api, Authorino and Limitador sampled every ~10s; the ramp would stop on any restart. None restarted at any level — Authorino peaked at 377m CPU, payload-processing at 46m of its 1-core limit.

What actually fails, and where

  1. The 60-second wall — AWS Classic ELB idle timeout. The gateway's LoadBalancer Service carries no aws-load-balancer-type: nlb annotation, so AWS built a Classic ELB; aws elb describe-load-balancer-attributes returns IdleTimeout: 60. Envoy's own route and stream timeouts are 0 (none). Because SSE is buffered, no byte crosses the ELB until generation ends, so any turn longer than 60s is cut with zero bytes. Every reset in the table lands at 60.3–60.6s.
  2. HTTP 500 on bursts of ~20+ simultaneous new requests. 16 at once: clean; 24: 17% fail; 32: 50% fail, each in 0.8s with a 23-byte body. Envoy's wasmcustom.kuadrant.errors counted exactly the failures, and Authorino logged them as UNAVAILABLE with no such key: identity while maas-api answered every callout in 0ms. Reading (inferred): the wasm shim's auth call has a 200ms deadline with failureMode: deny, and a burst pushes half the checks past it. Spread-out arrivals never triggered it. CPU was not the cause anywhere.
  3. No 429s. sa-premium allows 90,000 tokens/s for this model — fifteen times what the GPU can prefill — so the token limiter never bound.

Why requests wait while the KV cache is mostly empty

The LLM Performance dashboard shows num_requests_waiting climbing while kv_cache_usage_perc stays low. Both are true at once, because admission into the engine is limited by compute per step, not by memory:

  1. vLLM V1 runs in steps. Each step has a token budget, max_num_batched_tokens. We pass none, and on a GPU with ≥70 GiB vLLM picks 8,192 for the API server (engine/arg_utils.py; the pod log says Chunked prefill is enabled with max_num_batched_tokens=8192).
  2. Requests already running are served first: one token for each one decoding, and the next chunk for each one still prefilling. A single 20k-token cold prompt eats the whole 8,192 in one go.
  3. Only then are waiting requests admitted, while token_budget > 0 (v1/core/sched/scheduler.py, line 897). With the budget at zero the loop exits — nobody new starts, however much KV is free.
  4. The other two gates are far away: max_num_seqs is 1,024 on an H100 (we never exceeded 32 running), and KV allocation never failed (peak 22% while requests waited).
  5. vLLM's own label agrees once you read its definition: num_requests_waiting_by_reason{reason="capacity"} means "waiting for scheduling capacity" — budget, sequence slots or KV. Across 150 five-second samples with a queue, capacity summed to 1670 and deferred to 0, with KV never above 22%.

The 100-agent run, from the engine's own 10-second log. Prompt throughput holds at a median 5,614 tokens/s across the 29 ten-second intervals with a queue (the rest are windows where a burst started or ended) — the GPU's prefill rate, pinned. Running grows by ~5 every 10s: that is how fast 20k-token prompts can be prefilled, so in 60s about 30 get started. That is why running peaks at 31 at 48, 64 and 100 agents alike — not a limit, just how many fit before the ELB fires. Then the clients are cut, vLLM aborts, running collapses, and the queue (60+) drains as aborts rather than answers.

So "waiting" with free KV is not a misconfiguration. It is the visible end of a prefill-bound queue. More KV would not admit anyone sooner; more prefill compute per second would.

Levers, in order of payoff

  1. Stop buffering SSE gateway-wide — drop the api-translation response plugin or isolate the Anthropic model. Bytes then flow during generation, the ELB never sees a 60s silence, users see tokens as they come, and the wall at ~30 agents becomes a slow-down instead of a failure. Zero GPU cost.
  2. Raise the ELB idle timeout (service.beta.kubernetes.io/aws-load-balancer-connection-idle-timeout through the Gateway's infrastructure annotations) or move the Gateway to an NLB. Same effect on failures as lever 1, without fixing streaming.
  3. More GPUs and replicas. Prefill is the binding resource; the EPP is prefix-cache aware, so sessions stay with the replica holding their history and capacity scales close to linearly.
  4. Raise the auth deadline or add Authorino replicas for burst tolerance — only matters when many agents start in the same second.
  5. Not scheduler tuning (shown above), and not MIG: two slices each get about half the prefill rate.
